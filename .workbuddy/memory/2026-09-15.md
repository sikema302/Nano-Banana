### 本机网络环境的重大发现（重要，以后复用）

- 本机 Agent 的 bash **没有直连外网能力**，所有出网流量走本地 HTTP CONNECT 代理
  `http_proxy/https_proxy = http://127.0.0.1:49766`。
- 该代理 **允许 CONNECT 到任意 host:port**（含 22 端口），因此可以用它做任意 TCP 隧道。
- 写了一个本地转发器：`C:\Users\刘兆朋\.workbuddy\ssh-tunnel.mjs`
  用法：`node ssh-tunnel.mjs <listenPort> <targetHost> <targetPort>`
  例：`node ssh-tunnel.mjs 2222 23.141.172.73 22` → 然后 `ssh -p 2222 root@127.0.0.1`。
  （Windows 下给 node 传路径必须用 `C:/...` 形式，用 `/c/...` 会被解析成 `d:\c\...` 而 MODULE_NOT_FOUND。）
  后台运行必须用 `run_in_background=true`，用 `&` 会随命令结束被杀掉。
- **但目标服务器拒绝了本机/代理的 SSH**：TCP 能连上 22 端口，但在
  `kex_exchange_identification` 阶段被 RST。对照测试（同样经代理连 github.com:22）
  能正常拿到 SSH banner，证明隧道本身没问题 → 是**服务器侧按来源 IP 拦截**（fail2ban /
  安全组 / hosts.deny 之类）。源站 443 直连也超时（疑似只放行 Cloudflare 回源）。
- 结论：**Agent 无法直连该服务器**，服务器排查只能由用户在宝塔面板终端里手动执行脚本。
- `WebFetch` 工具走的是宿主/云端网络，不受上述限制，可以正常读到 `https://pixory.top/api/health`。

## 已实施的修复（同日晚）

结论先说：**那条具体记录的真实报错已经不可恢复**——旧代码把 `error_detail` 也写成了笼统文案。
本地也没有生产凭据（`.env.local` 里 R2_*/SUPABASE_* 全是空串或占位符），
所以只能从代码层把「这一整类失败」根治掉。改动如下：

1. **新增 `server/generation-failure.ts`（纯函数 + 单测 `generation-failure.test.ts`）**
   `resolveGenerationFailureStage({upstreamSucceeded, imagePersisted, creditsCharged})`
   → `'upstream' | 'persist' | 'charge' | 'post-charge'`，每个阶段一句独立文案。
   原则：文案必须讲清「钱和图」——persist 阶段明确写「本次未扣积分」，绝不出现「已扣除积分」。
2. **`markGenerationRequestFailed` 不再覆盖根因**（index.ts + supabase-db.ts）
   新增 `options.detail`：`result_message` 放人话结论，`error_detail` 放
   `"stage=persist Download generated image failed (404)"` 这类真实根因。
3. **后台展示语义修正**（`src/App.tsx` 约 5179 行）
   单元格显示 `resultMessage`（结论），tooltip 显示 `errorDetail`（根因）。
   旧代码两者都优先取 errorDetail，等于人话文案永远看不到。
4. **`writeGeneratedImageToR2` 增加 R2 全失败时的本地磁盘降级**（`R2_LOCAL_FALLBACK`，默认 true）
   把已拿到手的 buffer 写 `uploads/generated/` 并照常交付，用户不再「上游出了图却拿不到」。
   `IS_VERCEL` 或 `R2_LOCAL_FALLBACK=false` 时保持原严格行为。抽出了 `writeGeneratedImageLocally()` 复用。
5. **降级必须可观测**：模块级计数 + `/api/health` 新增
   `generatedImageStorage: { localFallbackEnabled, localFallbackCount, lastLocalFallbackAt, lastLocalFallbackReason }`，
   日志打 `[r2-fallback]`；另有结构化 `[generate-failed] stage=... requestId=... : detail` 一行。
6. `.env.example` 补 `R2_LOCAL_FALLBACK` 说明，并把「never stored locally」改成「除降级外不落本地」。

## 回归复查（同日晚，用户问「会不会影响以前的功能」）

复查中发现上一轮改动的一个**生产级疏漏并已修复**：

- `server/index.ts:6719` 在 `R2_STORAGE` 存在时，把 `/uploads/(generated|thumbnails)/*`
  **302 跳到 R2 公网地址**（用于兼容历史 DB 里存 `/uploads/...` 路径的行）。
- 而本地降级写下来的图 R2 里根本没有 key → 用户拿到的是**裂图**（比原来的明确报错更糟）。
- 修法：该路由先 `pathExists(path.join(UPLOADS_DIR, key))`，本地有文件就 `next()` 交给
  `express.static(UPLOADS_DIR)` 读盘，否则维持原样 302。
- **实测验证**（用假 R2 凭据起服务，避免本地 `.env.local` 未配 R2 导致该路由不挂载）：
  `uploads/generated/smoke-local-serving-test.png` 存在 → **200**；不存在 → **302 Location:
  https://img.example.com/generated/no-such-file-xyz.png**（老行为保持）。
- 复查结论：`readImageAsBase64`（6220）本来就本地优先，Gemini 兼容接口不受影响；
  `purgeExpiredGeneratedFiles`(4622) 与 `enforceDiskPressure`(4676) 都会清本地
  `uploads/generated`，降级图不会无限堆积。
- 已知小瑕疵（未改，风险可控）：`purgeExpiredGeneratedFiles` 要求**本地缩略图存在**才删原图
  （4639），若 sharp 生成缩略图失败，该文件只能等 85% 磁盘应急清理兜底。
- 生产端确认：`https://pixory.top/api/health` **没有** `generatedImageStorage` 字段
  → 本次改动尚未部署，线上仍是老代码。
