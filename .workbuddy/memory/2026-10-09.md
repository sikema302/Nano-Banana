## 排查：uselg 生图仍在用旧 key（sk-a29f…）

用户发现 gpt 1K 请求到 uselg 时仍在用旧 key `sk-a29f9961…`，而非新 key `sk-86bc3316…`。

**结论：代码没问题，key 不是硬编码，真实来源是 GitHub Actions Secrets。**

链路（生产）：
- 仓库全局搜不到这两个 key 字符串（0 匹配）→ 不是硬编码。
- `server/index.ts`：`USSELG_STANDARD_KEY`（1K/STANDARD 用）、`USSELG_HD_KEY`（2K/4K 用），由 `selectUselgApiKey()` 按尺寸选。
- `.github/workflows/deploy-production.yml` L23-24 从 `secrets.USSELG_STANDARD_KEY / USSELG_HD_KEY` 读取 → L78-80 写入 `.secrets/uselg-env` → 打包进 release。
- 服务器 `deploy.sh` L129-135 用 `.secrets/uselg-env` 覆盖 `.env.local` 的这两个变量 → pm2 restart 生效。
- 本地 `.env.local` 里这两个变量是空字符串（本地不配 key）。

**根因：GitHub 仓库 Settings → Secrets → Actions 里的 `USSELG_STANDARD_KEY` 仍是旧值，未更新成新 key。** 每次部署都会被旧 secret 重新覆盖回 `.env.local`，所以请求还是旧 key。

**修复**：改 GitHub secret `USSELG_STANDARD_KEY` 为新 key，然后重新部署（push main 或手动触发 "Deploy production"）。临时立即生效可服务器改 `.env.local` + `pm2 restart nano-banana --update-env`，但下次部署会被 GitHub secret 覆盖回旧值。

易踩坑：改任何渠道的 key，一定要改到 GitHub Actions Secrets（而非本地 .env / 服务器 .env.local），否则重新部署即回退。

## 性能诊断：接口/图片慢（服务器不慢，根因是网络路径）

用户反馈接口请求慢、图片慢。线上 `/api/health` 探针证实服务器几乎空闲：CPU 0.4%、内存 36.5%（可用 5GB）、eventLoopLag 20ms、队列 active=1/pending=0。→ **慢不在算力，在网络路径。**

关键事实（已确认）：
- 数据库 = **本地 SQLite**（`DATABASE_PROVIDER=sqlite`，health 返回 `userStorage: SQLite`），存在服务器磁盘 `/var/www/nano-banana/data/`，不是云端。表有基本索引（created_at/user_id/request_id）。
- 图片 = **Cloudflare R2 直链**，前端 `<img src={thumbnailUrl||imageUrl}>` 直连 `R2_PUBLIC_BASE_URL`（`r2-storage.ts` publicUrl），**不经服务器/nginx 反代**。对象上传带 `Cache-Control: public,max-age=31536000,immutable`。
- 架构：香港服务器 23.141.172.73 → Cloudflare 回源 → Node(3001) → 上游生图渠道（junliai/schat/uselg，均海外）。
- 生图接口 `/api/generate` 慢是**正常**（等上游海外渠道出图 10-60s）。

根因判断：
- 图片慢头号嫌疑 = R2 publicBaseUrl 若用默认 `*.r2.dev`（无 CDN 缓存、不保证 SLA）每次回源跨境慢；自定义域名走 Cloudflare 边缘缓存会好很多。
- 查询接口慢 = 香港↔大陆跨境延迟，非算力。
- 待确认分叉点：R2_PUBLIC_BASE_URL 是 r2.dev 还是自定义域名？用户主要从大陆还是海外访问？

## 续3：大陆直连实测通过，方案拍板

用户从大陆 ping 23.141.172.73：**平均 70ms（最低 51ms），0% 丢包** → 线路优秀，直连方案成立。
对比走 CF 首字节 1.4~7.3s，直连快 30~100 倍。

最终方案（灰云直连）：
1. **先确认服务器证书类型**（openssl -issuer）：若为 Cloudflare Origin CA 签发，灰云后浏览器不信任，需换 Let's Encrypt（宝塔一键）；若是公网 CA 则直接可用。
2. CF DNS：pixory.top / www.pixory.top A 记录（23.141.172.73）改灰云 DNS only。
3. 图片先不动（img.pixory.top 是 R2 自定义域名必须走 CF）；若仍慢再做服务器反代 R2（改 R2_PUBLIC_BASE_URL 指向 pixory.top/r2-img/ + nginx 反代）。
4. 灰云代价：失去 CF 的隐藏源站 IP 与 DDoS 防护。

## 续4：直连 443 稳定性翻车，灰云暂缓（关键发现）

用户大陆实测：ping 51ms/0丢包（网络层优），但 `curl https://23.141.172.73/` 总耗时 **2.06s**（TLS 层慢）。
沙箱模拟灰云直连（--resolve pixory.top→23.141.172.73，带正确 SNI）连测 6 次：
**2 次完全失败（8s 超时），4 次 1.5~11.2s**（TLS 握手 0.5~4.4s）。极不稳定。
（早些时候测到 0.2-0.3s 的快速响应无法复现，疑似偶然放行。）

判断：ping 通但 TLS 慢/失败 → 最大嫌疑 = **服务器防火墙对非 Cloudflare IP 的限制**
（与旧记忆"443 只放行 CF 回源"吻合，早前 0.2s 快速响应可能是临时放行）；次嫌疑 = 跨境 TLS 大包（证书链）丢包重传。

下一步（灰云前置条件）：
1. 服务器查防火墙：宝塔 → 安全 / `iptables -L INPUT -n | head -30` / 云厂商安全组，看 443 是否仅放行 CF IP 段。
2. 用户大陆多测几次直连稳定性（`curl -k -o NUL -s -w "..." https://23.141.172.73/`）。
3. 若无防火墙限制 → TLS 优化：换 ECC 证书、nginx OCSP stapling、MSS clamp。
**灰云必须等直连稳定（多测 <0.5s 且 0 失败）后再切，否则用户会经常打不开站。**

## 续5：灰云绿灯放行（最终结论）

用户大陆 5 次 curl 直连（`-k https://23.141.172.73/`）：**5/5 成功，总计 0.16s / 0.22s / 0.94s / 1.25s / 1.36s**；TCP 47-124ms，TLS 首次 1.2s（首次完整握手）、后续 0.10-0.17s（session 复用后快）。
服务器防火墙 = UFW（policy DROP），但 443 实际对公网放行（用户能连上即证明），**防火墙不是问题**。
沙箱直连的失败是出口环境个案，不代表大陆用户。对比走 CF 1.4~7.3s：**直连全面胜出 → 灰云方案成立。**

最终动作清单：
1. CF DNS：pixory.top / www 两条记录橙云→灰云（img.pixory.top 不动）。
2. 预期：接口 1.4-7.3s → 大部分 50-200ms（浏览器有连接复用，体感好于 curl 数据）。
3. 可选优化（灰云后）：换 ECC 证书 + nginx OCSP stapling，消 TLS 首次握手 1.2s 抖动。
4. 图片后续：img.pixory.top 仍走 CF；若慢再做服务器反代 R2。
