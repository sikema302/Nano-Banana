## 创作页多张图片改为"多灶台并行生成"

**问题**：PIXORY 创作页设置数量=3 时，UI 只显示 1 个灶台 + "第 2/3 张 47%"，是一张一张顺序生成的。用户要求：数量=3 应"立马占据 3 个灶台异步同时生成"。

**根因**：`src/App.tsx` 的 `handleGenerate` 用 `for + await` 串行循环；且 UI 层把一次批量当作**单个** ActiveImageGeneration（progress.total=N），只占 1 个灶台。

**最终方案**（分两个阶段完成，第一版只改数据层并行、UI 仍是 1 灶台，第二版才彻底拆灶台）：

1. **一次批量拆成 N 个独立 generation**：`batchGenerationIds`（N 个 id），每个 `progress.total=1`，提交时 `setActiveImageGenerations` 一次性 push N 个灶台。
2. **两阶段并行**：
   - 阶段 1：`Promise.allSettled` 并行调用 `startGenerateImageJob`（N 个 POST 同时发出）
   - `releaseSubmission()` 在所有提交完成后立即释放提交锁（保留"再来一批"能力）
   - 阶段 2：`Promise.allSettled` 并行轮询，每个 job 用 `total=1` 独立更新对应灶台（`updateGenerationSlot(id, ...)`）
3. **灶台占位逻辑修正**（`activeGenerationStageEntries`）：`completed >= total` 的 generation 只展示图片、不再追加"进行中"占位，否则会多出一个空灶台。
4. **错误处理**：`allSettled` 区分"全部失败 throw→catch"与"部分失败→继续 commit 成功图片 + 顶部红字轻提示"；失败灶台标记 `completed=1` 避免一直转圈。
5. **finally**：清理所有 `batchGenerationIds`。

**后端确认**：`/api/generate/jobs` 是异步队列（POST 立即返回 202），`generationWorkQueue` 并发上限 `GENERATION_MAX_CONCURRENCY=10`，足以同时接 3 个任务。

**验证**：`npx tsc --noEmit` 通过。

**文件**：`src/App.tsx`（handleGenerate 约 6516-6662，activeGenerationStageEntries 约 7058）。

## 本地开发存储兜底（无 R2 凭据也能启动）

**问题**：本地 `.env.local` 的 R2 五项凭据是空字符串 `""`，`start()` 硬性检查 `if (!R2_STORAGE) throw` 导致后端无法启动，前端所有 API 走 vite proxy 报 ECONNREFUSED。

**改动**（`server/index.ts`，用 `!R2_STORAGE` 判断隔离，生产有 R2 时完全不受影响）：
1. `start()` 的 R2 检查改为 `if (!R2_STORAGE && IS_VERCEL)` —— 本地开发允许无 R2。
2. `writeGeneratedImageToR2` 增加本地兜底：无 R2 时写 `uploads/generated/` + `uploads/thumbnails/`，返回 `/uploads/generated/xxx`（经 `/uploads` express.static 服务）。
3. 启动日志 `[image-storage] provider=...` 与 `/api/health`、`/api/ready` 的 `imageStorageProvider` 字段改为动态返回（r2 / local-filesystem）。

**验证**：`npx tsc --noEmit` 通过；后端启动成功 `provider=local-filesystem`；`/api/health` 返回 ok，`/api/models` 经 vite proxy 返回 401（需登录，符合预期）。

**注意**：本地图片存 `uploads/` 目录，未持久化到云；部署环境仍需真实 R2 凭据。

## 接入 GPT-image-2.5（Flare / Sunburst）

**接入设计**：
- 两种模式 `GPT-image-2.5-Flare`（更快）和 `GPT-image-2.5-Sunburst`（思考更久）
- 清晰度 1K/2K/4K；质量 auto/low/medium/high（与 GPT-image-2 一致）
- **1K 走 junliai**（`gpt-image-2.5-flare` / `gpt-image-2.5-sunburst`），**2K/4K 走 firefly**（`firefly-gpt-image-2.5-flare` / `firefly-gpt-image-2.5-sunburst`）
- 积分沿用 `GptImagePricing`（standard 20 / twoK 28 / twoKHigh 48 / fourK 34 / fourKHigh 48）
- 路由通过 `primaryModelCapabilities` 按 imageSize 自动过滤：junliai 上游 `imageSizes: ['1K']`、firefly 上游 `imageSizes: ['1K','2K','4K']`

**改动文件**：
- `server/image-provider-router.ts`：firefly 匹配改 `startsWith('firefly-gpt-image-2')`；`primaryEligible` 加入两个新 modelId
- `server/index.ts`：models 数组加两条；router 配置 `primaryModels` / `primaryModelChains` / `primaryModelCapabilities` 加 4 个上游；`isPrimaryModelEnabled` firefly 走 junliai-firefly；`normalizeImageSize` 加 2 个 modelId
- `src/lib/model-credit-config.ts`：`getConfiguredImageCredits` 加 2 个 modelId
- `src/App.tsx`：defaultModels 加两条；`getModelCredits`、`showGptQuality`、`selectedCreditBucket`、`handleModelSelect`、`getModelSuccessRate` 全部扩展
- `src/BatchCreateView.tsx`：availableModels、creditBucket 加 2 个 modelId

**验证**：`npx tsc --noEmit` 通过；tsx watch 自动重启后 `Visionary server listening on http://0.0.0.0:3001` + `[image-storage] provider=local-filesystem`。

**注意**：junliai 上游真实 model 名是截图里的 `gpt-image-2.5-flare` / `gpt-image-2.5-sunburst` 等；firefly 上游是 `firefly-gpt-image-2.5-flare` / `firefly-gpt-image-2.5-sunburst`（前端已读懂用户截图）。真实调用需在生产 R2 凭据下才能完整测试，本地未配置上游 API Key。

## 修复：GPT-image-2.5 积分始终显示 28

**根因**：前端 `src/App.tsx` 的 `getModelCredits` 和 `src/BatchCreateView.tsx` 的 `getCredits` 只给 `gpt-image-2` 接了 `getConfiguredImageCredits`，GPT-image-2.5-* 落到 `model.creditsCost`（后端 /api/models 按 2K 默认返回 28），导致切 1K/2K/4K 积分都不变。

**修复**：两处函数把 `GPT-image-2.5-Flare` / `GPT-image-2.5-Sunburst` 并入 GPT-image-2 系列分支，走 `getConfiguredImageCredits`（imageSize 默认 '1K'），积分随清晰度正确变化（1K=20 / 2K=28或high48 / 4K=34或high48）。
