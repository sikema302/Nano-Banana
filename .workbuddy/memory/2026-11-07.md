## 发现的存量问题（未改，需用户决策）

1. **2.5/2.6 扩展比例会被后端吞成 1:1**：前端 2.5/2.6 提供 5:4、4:5、3:1、1:4、4:1 选项，
   但 `server/index.ts` 的 `normalizeRatio` 白名单只有 8 个基础比例
   （16:9/9:16/1:1/4:3/3:4/3:2/2:3/21:9），其余一律归一成 '1:1'，且路由器
   `IMAGE_SIZES` 像素表也没有这些比例的档位 → 用户选 5:4 实际出 1:1 方图。
   自 fa9ebdc（2026-09-12 引入 2.5）即存在，已在线上跑近两个月。
   修复需：normalizeRatio 放行 + IMAGE_SIZES 补 5:4/4:5/3:1/1:4/4:1 像素档。
2. **2.5 前后端积分池口径不一致（2.6 同样继承）**：前端把 2.5/2.6 归 'gpt' 池展示
   （gpt+general），后端 `creditBucketForModel` 对 2.5/2.6 返回 'general'
   （只查/扣 general 池）。用户 GPT 专用积分多、general 为 0 时前端显示够扣、后端拒单。

## 2.6 的 2K/4K 前端暂时禁用（commit b052037，本地未 push）

需求：先只开放 2.6 的 1K，2K/4K 在界面上不可选；**后端不动**（公开 API 的 2K/4K 能力保持）。

- 唯一开关是 `GPT_IMAGE_2_6_ENABLED_SIZES = ['1K']`，两处各一份、需同步：
  `src/App.tsx`（`ReadonlyArray<ImageSizeOption>`）与 `src/BatchCreateView.tsx`（`ImageSize[]`）。
- 创作页三处联动：`visibleResolutionOptions` 过滤渲染、`isImageResolutionEnabled` 对 2.6 的 2K/4K 返回 false、
  `useEffect` 兜底（历史记录回填 / 编辑复用带入 2K/4K 时回退 1K）。
- 批量页：`resolutionOptions` 里 `isGpt26 && !GPT_IMAGE_2_6_ENABLED_SIZES.includes(resolution)` 直接排除。
- **踩过的弯路**：一开始顺手让 `server/index.ts` 的 `normalizeImageSize` 把 2.6 一律归 1K，
  用户明确要求「后端不动」，已 `git checkout -- server/index.ts` 回滚。
  现状：公开 API 传 imageSize=2K/4K 仍真的走 firefly 并按 2K/4K 档计费，只是前端选不到。
- 恢复 2K/4K：把档位加回两个常量数组即可，渠道组 / 比例表 / 计价档位都已就绪。
